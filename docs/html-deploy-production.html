Production deploy — Docker Compose behind a Cloudflare Tunnel

Put the full stack on a VPS and expose it at a real hostname without opening port 80 or 443, without a public IP, and without ever running certbot. cloudflared dials out to Cloudflare; nothing dials in.

Why a tunnel instead of open ports

docs/how-to-deploy.md covers the classic route: publish port 80/443 and issue a Let's Encrypt certificate. This guide replaces that edge entirely. Both end at the same four containers.

 Port-forward + certbotCloudflare Tunnel
Inbound ports 80 + 443 open to the internet None — outbound only
Public IP Required Not required — works behind NAT/CGNAT
TLS certificate certbot + renewal cron on the box Managed by Cloudflare, auto-renewed
Origin IP exposure Visible in DNS Hidden — DNS points at the tunnel
DDoS / WAF Yours to solve Cloudflare edge, free tier included
SSO in front of the app Build it yourself Cloudflare Access (optional, see §13)
Dependency None beyond your VPS Cloudflare — they are now in your critical path
Cost Free Free tier is sufficient here
The honest trade-off: you swap "I manage certificates and a firewall" for "Cloudflare can see my traffic and is a hard dependency." For an internal IT operations dashboard that is almost always the right trade. For something that must survive a Cloudflare outage, it is not.

1 Architecture

Five containers on a private opsnet bridge. Nothing is published to the host. cloudflared holds a persistent outbound connection to Cloudflare's edge and forwards requests to nginx:80 over the Docker network.

Published ports
0 — none
Certificates on VPS
0 — none
Containers
5 + cloudflared
Volumes
2 pgdata · uploads

nginx keeps its job unchanged: /api/ and /uploads/ to backend:3000, everything else to frontend:80. The SPA calls a relative /api, so there is still no build-time API URL to configure.

2 Prerequisites

  • A VPS running Ubuntu 24.04 LTS with a sudo-capable user () — don't deploy as root.
  • ~2 GB RAM. Postgres + Bun + two nginx + cloudflared. 1 GB will build but may OOM during bun install.
  • Outbound access on TCP/UDP 7844 to Cloudflare — QUIC preferred, falls back to HTTPS. Most VPS providers allow this by default.
  • A domain on a Cloudflare account, with its nameservers already pointed at Cloudflare (the zone must be Active).
  • Inbound 22 (SSH) only. 80 and 443 stay closed for good.
No public IP needed. This works from a home server behind CGNAT just as well as from a datacentre VPS. That is the point of a tunnel.

5 Compose: unpublish nginx, add cloudflared

Two edits to docker-compose.yml. Keep everything else exactly as it is.

5.1 — Remove the published port from nginx

This is the edit that actually closes the door. With a tunnel, publishing 80 to the host is not just unnecessary — it is a bypass around every Cloudflare protection you are about to configure.

docker-compose.yml — nginx serviceyaml
  nginx:
    image: nginx:1.27-alpine
    restart: unless-stopped
    # ports:                    ← DELETE this block entirely.
    #   - "80:80"                  cloudflared reaches nginx over opsnet,
    #                              not through the host.
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
    depends_on: [frontend, backend]
    networks: [opsnet]

5.2 — Add the cloudflared service

docker-compose.yml — append under services:yaml
  cloudflared:
    image: cloudflare/cloudflared:latest
    restart: unless-stopped
    # --no-autoupdate: the image is the update mechanism; let Compose pull it.
    command: tunnel --no-autoupdate --loglevel info run
    environment:
      TUNNEL_TOKEN: ${CLOUDFLARE_TUNNEL_TOKEN:?set CLOUDFLARE_TUNNEL_TOKEN in .env}
      # Metrics endpoint for the health probe below.
      TUNNEL_METRICS: 0.0.0.0:2000
    depends_on: [nginx]
    networks: [opsnet]
    healthcheck:
      test: ["CMD", "cloudflared", "--version"]
      interval: 30s
      timeout: 5s
      retries: 3
Why TUNNEL_TOKEN as an environment variable rather than --token on the command line? A token passed as an argument shows up in docker inspect, ps aux on the host, and your shell history. The env var is still readable by anyone who can run Docker, but it stops leaking into process listings.
Prefer config files over a dashboard token? See §7 Option B — a locally-managed tunnel with config.yml and a credentials JSON, mounted read-only. It keeps routing in git; it also means the dashboard can't change your routes.

6 nginx: real client IPs and the right scheme

Behind a tunnel, every request arrives from the cloudflared container's Docker IP over plain HTTP. Two headers need fixing or your logs lie to you and the backend thinks it's on http.

nginx/conf.d/default.confnginx
# Cloudflare puts the true client IP here; cloudflared forwards it.
# Trust it only from the Docker bridge ranges — never from the internet.
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 172.16.0.0/12;
set_real_ip_from 192.168.0.0/16;
real_ip_header CF-Connecting-IP;
real_ip_recursive on;

# The edge terminated TLS, so $scheme here is "http" and would be wrong.
# Trust the forwarded value, falling back to $scheme for local curl tests.
map $http_x_forwarded_proto $fwd_proto {
    default $scheme;
    https   https;
    http    http;
}

server {
    listen 80;
    server_name _;                # the tunnel decides the hostname

    client_max_body_size 12m;     # floor-plan uploads up to 10 MB

    gzip on;
    gzip_comp_level 5;
    gzip_types text/css application/javascript application/json image/svg+xml;

    add_header X-Frame-Options SAMEORIGIN always;
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;

    location /api/ {
        proxy_pass http://backend:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $fwd_proto;   # ← was $scheme
        proxy_read_timeout 60s;
    }

    location /uploads/ {
        proxy_pass http://backend:3000;
        proxy_set_header Host $host;
        expires 7d;
        add_header Cache-Control "public";
    }

    location / {
        proxy_pass http://frontend:80;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $fwd_proto;   # ← was $scheme
    }
}
Delete the commented-out 443 block at the bottom of the existing file. With a tunnel there is no certificate on this box and that block can only ever mislead the next person to read it.

7 Create the tunnel

Two ways. Option A (dashboard) is faster and self-heals if you change routes. Option B (CLI) keeps routing in version control. Pick one.

Option A — remotely-managed, via the Zero Trust dashboard

  1. Go to one.dash.cloudflare.com → Networks → Tunnels → Create a tunnel.
  2. Choose Cloudflared as the connector type.
  3. Name it → Save.
  4. On the install screen, ignore the install commands — copy the token (the long string after --token) into CLOUDFLARE_TUNNEL_TOKEN in your .env.
  5. Open the Public Hostnames tab → Add a public hostname:
FieldValue
Subdomainops (whatever is left of your zone)
Domainyour zone, e.g. example.com
Pathleave empty
TypeHTTP
URLnginx:80  container name, not localhost
The single most common mistake: entering localhost:80 or 127.0.0.1:80 as the service URL. Inside the cloudflared container, localhost is that container — not nginx, not the host. It must be nginx:80, resolved by Docker's DNS on the shared opsnet network. This is also why cloudflared must be on networks: [opsnet].

Saving the public hostname creates the DNS record for you — §8 is then just verification.

Option B — locally-managed, config in git

on the VPS — one-time, interactivebash
# Authenticate: prints a URL, opens a browser, pick your zone.
# Writes ~/.cloudflared/cert.pem
docker run -it --rm -v ~/.cloudflared:/home/nonroot/.cloudflared \
  cloudflare/cloudflared:latest tunnel login

# Create the tunnel — writes ~/.cloudflared/<TUNNEL-ID>.json
docker run -it --rm -v ~/.cloudflared:/home/nonroot/.cloudflared \
  cloudflare/cloudflared:latest tunnel create {{tunnel}}

# Route DNS at it (creates the proxied CNAME)
docker run -it --rm -v ~/.cloudflared:/home/nonroot/.cloudflared \
  cloudflare/cloudflared:latest tunnel route dns {{tunnel}} {{domain}}
cloudflared/config.ymlyaml
tunnel: <TUNNEL-ID>
credentials-file: /etc/cloudflared/<TUNNEL-ID>.json

ingress:
  - hostname: {{domain}}
    service: http://nginx:80
  # Catch-all is REQUIRED and must be last, or cloudflared won't start.
  - service: http_status:404
docker-compose.yml — Option B variantyaml
  cloudflared:
    image: cloudflare/cloudflared:latest
    restart: unless-stopped
    command: tunnel --no-autoupdate --config /etc/cloudflared/config.yml run
    volumes:
      - ./cloudflared:/etc/cloudflared:ro
    depends_on: [nginx]
    networks: [opsnet]
Add cloudflared/*.json to .gitignore. The credentials file is the tunnel's private key. Committing it hands anyone with repo access the ability to serve traffic on your hostname.

8 DNS

Either path above created the record. You are verifying, not creating — unless something went wrong.

In the Cloudflare dashboard → your zone → DNS → Records:

TypeNameTargetProxyTTL
CNAME ops <TUNNEL-ID>.cfargotunnel.com Proxied 🟠 Auto
The proxy toggle must be orange. A grey-cloud (DNS-only) .cfargotunnel.com record cannot resolve for visitors — that hostname only means something inside Cloudflare's network. Grey cloud here produces an immediate, total outage with a confusing NXDOMAIN.

Check it from your laptop:

localbash
dig +short {{domain}}
# → two Cloudflare anycast IPs (104.x / 172.67.x), NOT your VPS IP.
#   Seeing your VPS IP means the record is grey-clouded or points at an A record.

SSL/TLS mode

Zone → SSL/TLS → Overview → set encryption mode to Full (strict). The edge-to-origin hop runs inside the tunnel's own encrypted connection, so there is no origin certificate to install — but Flexible is still the wrong choice and can produce redirect loops. While you're there, turn on Always Use HTTPS.

schema + first adminbash

# Create exactly one admin user — no demo data
docker compose exec \
  -e ADMIN_EMAIL=you@company.com \

It refuses under NODE_ENV=production (which the backend Dockerfile sets), and the demo bundle it needs (_extracted/) is gitignored — two guards you should not go looking for a way around. db:seed:admin is the production command.

10 Google sign-in (optional)

Leave GOOGLE_CLIENT_ID blank to skip this entirely — GET /api/auth/providers reports {google:false} and the button disappears from the login page.

  1. Google Cloud Console → APIs & Services → Credentials → Create OAuth client ID → Web application.
  2. Authorised JavaScript origins: https://
  3. Authorised redirect URIs — must match byte-for-byte: https:///api/auth/google/callback
  4. Put the client ID and secret in .env, then docker compose up -d backend.
.env — Google blockenv
GOOGLE_CLIENT_ID=1234567890-abcdef.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=GOCSPX-xxxxxxxxxxxxxxxx

# Only this email domain is auto-provisioned on first Google sign-in.
# Leave BLANK and no new accounts are ever created automatically —
# existing users can still link their Google identity and sign in.
GOOGLE_ALLOWED_DOMAIN=company.com
Where the redirect URI comes from: backend/src/lib/google-oauth.ts:35-37 builds it as FRONTEND_URL + /api/auth/google/callback. If your Cloudflare hostname differs from FRONTEND_URL for any reason, override it explicitly with GOOGLE_REDIRECT_URI — but note that docker-compose.yml does not currently pass that variable through to the backend, so you'd need to add it to the service's environment: block first.

11 Close the firewall

The tunnel is only a security win if the front door is actually locked. Nothing needs to reach this box from the internet except SSH.

on the VPSbash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp        # SSH — do NOT lock yourself out
sudo ufw enable
sudo ufw status verbose

# 80 and 443 are deliberately absent. If a previous deploy opened them:
sudo ufw delete allow 80/tcp
sudo ufw delete allow 443/tcp
ufw does not filter published Docker ports. Docker writes its own iptables rules ahead of ufw's chain, so a container with ports: "80:80" stays reachable from the internet even with ufw denying 80. That is exactly why §5.1 deletes the ports: block rather than relying on the firewall. Confirm nothing is published:
verify nothing is exposedbash
docker compose ps --format 'table {{.Service}}\t{{.Ports}}'
# The PORTS column must be empty for every service.

sudo ss -tlnp | grep -E ':(80|443)\s'
# Should print nothing at all.

13 Cloudflare hardening

Optional, but this is most of the value of routing through Cloudflare at all.

Cloudflare Access — SSO in front of the whole app

Zero Trust → Access → Applications → Add an application → Self-hosted. Point it at and add a policy such as emails ending in @company.com. Visitors now authenticate at Cloudflare's edge before a single request reaches your VPS.

Access sits in front of the API too — including /api/auth/google/callback, which Google needs to reach without a session. If you enable Access and Google sign-in, add a Bypass policy for the path /api/auth/google/*, or the OAuth round-trip will dead-end at a Cloudflare login screen.

Cache rules

The SPA's hashed assets are safe to cache; the API never is. Zone → Caching → Cache Rules:

  • Bypass cache when URI path starts with /api/
  • Bypass cache when URI path starts with /uploads/ — or cache it; nginx already sets expires 7d, and floor plans rarely change

WAF and rate limiting

  • Security → WAF → enable the Cloudflare Managed Ruleset.
  • Add a rate-limiting rule on /api/auth/login — say 10 requests per minute per IP. The app has no login throttling of its own, so this is your only brute-force defence.
  • Optionally restrict by country if all your staff are in one place.
Worth knowing about the app's session model: tokens are stateless 24-hour JWTs with no server-side session table, and authMiddleware never re-checks users.status. Suspending a user does not invalidate their existing token, and neither does signing out. Cloudflare Access is currently the only practical way to cut off a departing employee immediately.

Back up the database and uploads

backup.shbash
#!/usr/bin/env bash
set -euo pipefail
cd ~/{{dir}}
STAMP=$(date +%F-%H%M)
mkdir -p ~/backups

# Postgres logical dump
docker compose exec -T db pg_dump -U opsmonitor opsmonitor \
  | gzip > ~/backups/opsmonitor-$STAMP.sql.gz

# Uploaded floor-plan images (named volume, not a bind mount)
docker run --rm \
  -v ops-monitor_uploads:/data:ro \
  -v ~/backups:/out alpine \
  tar czf /out/uploads-$STAMP.tar.gz -C /data .

# Keep 14 days
find ~/backups -name '*.gz' -mtime +14 -delete
schedule itbash
chmod +x ~/backup.sh
( crontab -l 2>/dev/null; echo "15 3 * * * ~/backup.sh" ) | crontab -
The volume name is prefixed by the project name. docker-compose.yml declares name: ops-monitor, so the volumes are ops-monitor_uploads and ops-monitor_pgdata. Confirm with docker volume ls before trusting the backup script.
