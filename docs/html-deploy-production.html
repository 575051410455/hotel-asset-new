Production deploy — Docker Compose behind a Cloudflare Tunnel

The deploy host has no public IP, so there is nothing to forward a port to. It already runs a cloudflared connector for other services, and this stack reuses it — no second connector, no tunnel token here, no certbot, and the command never grows flags: docker compose up -d --build.

Why a tunnel instead of open ports

docs/how-to-deploy.md covers the classic route: publish port 80/443 and issue a Let's Encrypt certificate. That route is not available here — this host holds no public IP, so there is no inbound reachability to forward. The comparison is kept because it explains what the tunnel buys beyond solving that.

 Port-forward + certbotCloudflare Tunnel
Inbound ports 80 + 443 open to the internet None — outbound only
Public IP Required — we don't have one Not required — works behind NAT/CGNAT
TLS certificate certbot + renewal cron on the box Managed by Cloudflare, auto-renewed
Origin IP exposure Visible in DNS Hidden — DNS points at the tunnel
DDoS / WAF Yours to solve Cloudflare edge, free tier included
SSO in front of the app Build it yourself Cloudflare Access (optional, see §13)
Dependency None beyond your host Cloudflare — they are now in your critical path
Cost Free Free tier is sufficient here
The honest trade-off: you swap "I manage certificates and a firewall" for "Cloudflare can see my traffic and is a hard dependency." For an internal IT operations dashboard that is almost always the right trade. For something that must survive a Cloudflare outage, it is not.

1 Architecture

This project owns four containers on its private opsnet bridge. The fifth box below — cloudflared — is not ours: it already runs on this host for other services. Our nginx joins that connector's network () so it can be reached, and the connector forwards to it by container name.

Containers we run
4 + 1 reused
Tunnel tokens here
0 — none
Certificates on host
0 — none
Published ports
80 LAN only

nginx's job is unchanged: /api/ and /uploads/ to backend:3000, everything else to frontend:80. The SPA calls a relative /api, so there is no build-time API URL to configure.

Why port 80 is still published. With no public IP it reaches the office LAN only, and it is how you diagnose the app when the tunnel is down. On a host that does hold a public IP this must be deleted — it would bypass every Cloudflare protection below.

2 Prerequisites

  • A host running Ubuntu 24.04 LTS with a sudo-capable user () — don't deploy as root.
  • That host already running a healthy cloudflared connector, on a Docker network this project can join. scripts/preflight.sh reports both.
  • ~2 GB RAM. Postgres + Bun + two nginx + cloudflared. 1 GB will build but may OOM during bun install.
  • Outbound access on TCP/UDP 7844 to Cloudflare — QUIC preferred, falls back to HTTPS. Most VPS providers allow this by default.
  • A domain on a Cloudflare account, with its nameservers already pointed at Cloudflare (the zone must be Active).
  • Inbound 22 (SSH) only. 80 and 443 stay closed for good.
No public IP needed. This works from a home server behind CGNAT just as well as from a datacentre VPS. That is the point of a tunnel.

5 Join the connector's network

One edit to docker-compose.yml: nginx joins the network the existing connector is already on. There is no cloudflared service to add.

docker-compose.yml — nginx serviceyaml
  nginx:
    image: nginx:1.27-alpine
    restart: unless-stopped
    ports:
      # Kept deliberately: no public IP, so this is LAN-only and stays the
      # way in when the tunnel is down. DELETE on a host with a public IP.
      - "80:80"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d:ro
    depends_on: [frontend, backend]
    networks: [opsnet, {{network}}]
docker-compose.yml — networks blockyaml
networks:
  opsnet:

  # Created and owned by the stack that runs this host's cloudflared,
  # NOT by this file. external: true means "attach, don't create".
  {{network}}:
    external: true
This is a dependency on a project outside this repository. If that stack is torn down or renames the network, docker compose up here fails with network declared as external, but could not be found until this file is edited. That was the accepted trade for not running a second connector and not modifying a project this repo does not own.

Confirm the network name first

Don't take on faith — read it off the running connector:

on the hostbash
docker inspect -f '{{range $k,$v := .NetworkSettings.Networks}}{{$k}} {{end}}' \
  $(docker ps --format '{{.ID}} {{.Image}}' | grep -i cloudflared | awk '{print $1}')

# scripts/preflight.sh reports the same thing, with more context.
No override file, no COMPOSE_FILE, no -f. Because nothing about the topology differs between phases, one compose file covers both and the command stays docker compose up -d --build forever. Phase is expressed entirely by FRONTEND_URL and whether the hostname is mapped in the dashboard.

6 nginx: real client IPs and the forwarded scheme

Behind the tunnel, every request arrives from the connector's container IP over plain HTTP. Two directives fix what that hides. Both are already committed in nginx/conf.d/default.conf — this section explains them so the reasoning survives.

nginx/conf.d/default.conf — http contextnginx
# Cloudflare puts the true visitor IP in CF-Connecting-IP. Trust it ONLY
# from the Docker bridge ranges the connector can occupy.
#
# 192.168.0.0/16 is deliberately NOT trusted: port 80 stays published on
# the office LAN, which lives in that range, so trusting it would let any
# staff machine forge its own logged address — the very thing this guards.
set_real_ip_from 10.0.0.0/8;
set_real_ip_from 172.16.0.0/12;
real_ip_header CF-Connecting-IP;
real_ip_recursive on;

# The edge terminates TLS, so $scheme here is always "http". Forward the
# scheme the client actually used rather than the one we observed.
map $http_x_forwarded_proto $fwd_proto {
    default $scheme;
    https   https;
    http    http;
}
Be precise about what the scheme map does and doesn't fix. Nothing in the backend reads X-Forwarded-Proto today — the Google redirect_uri and the OAuth state cookie's secure flag both derive from FRONTEND_URL. This is hygiene, not a fix for a live bug. And unlike CF-Connecting-IP above, the value is accepted from any client; that is tolerable only while nothing consumes it. Guard it before anything does.

Inside the server block, both proxy locations pass proxy_set_header X-Forwarded-Proto $fwd_proto; instead of $scheme. There is no 443 block and no certificate on this host: the edge terminates TLS and the connector delivers plain HTTP to port 80.

Validate before restarting — a bad config stops nginx from coming back:
on the hostbash
docker run --rm -v "$PWD/nginx/conf.d:/etc/nginx/conf.d:ro" nginx:1.27-alpine nginx -t

7 Map the hostname on the existing tunnel

No tunnel is created here and no token is copied anywhere. You are adding one Public Hostname to the connector this host already runs.

  1. Go to one.dash.cloudflare.com → Networks → Tunnels.
  2. Open the tunnel that is already running on this host — the one scripts/preflight.sh reported, showing status HEALTHY.
  3. Open the Public Hostnames tab → Add a public hostname.

The single most common mistake: entering localhost:80 or 127.0.0.1:80. Inside the cloudflared container, localhost is that container — not nginx, not the host. It must be the container name, resolved by Docker's DNS on the shared network, which is exactly what §5 arranged.
Where ops-monitor-nginx-1 comes from. docker-compose.yml declares name: ops-monitor, and Compose names containers <project>-<service>-<n>. Confirm with docker compose ps --format '{{.Name}}' rather than assuming.

Saving the Public Hostname creates the DNS record for you — §8 is verification, not creation.

8 DNS

Either path above created the record. You are verifying, not creating — unless something went wrong.

In the Cloudflare dashboard → your zone → DNS → Records:

TypeNameTargetProxyTTL
CNAME ops <TUNNEL-ID>.cfargotunnel.com Proxied 🟠 Auto
The proxy toggle must be orange. A grey-cloud (DNS-only) .cfargotunnel.com record cannot resolve for visitors — that hostname only means something inside Cloudflare's network. Grey cloud here produces an immediate, total outage with a confusing NXDOMAIN.

Check it from your laptop:

localbash
dig +short {{domain}}
# → two Cloudflare anycast IPs (104.x / 172.67.x), NOT your VPS IP.
#   Seeing your VPS IP means the record is grey-clouded or points at an A record.

SSL/TLS mode

Zone → SSL/TLS → Overview → set encryption mode to Full (strict). The edge-to-origin hop runs inside the tunnel's own encrypted connection, so there is no origin certificate to install — but Flexible is still the wrong choice and can produce redirect loops. While you're there, turn on Always Use HTTPS.

  -e ADMIN_EMAIL=you@company.com \

  • the Device inventory lists and filters
  • a floor-plan image uploads and its pins place

10 Google sign-in (optional)

Leave GOOGLE_CLIENT_ID blank to skip this entirely — GET /api/auth/providers reports {google:false} and the button disappears from the login page.

  1. Google Cloud Console → APIs & Services → Credentials → Create OAuth client ID → Web application.
  2. Authorised JavaScript origins: https://
  3. Authorised redirect URIs — must match byte-for-byte: https:///api/auth/google/callback
  4. Put the client ID and secret in .env, then docker compose up -d backend.
.env — Google blockenv
GOOGLE_CLIENT_ID=1234567890-abcdef.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=GOCSPX-xxxxxxxxxxxxxxxx

# Only this email domain is auto-provisioned on first Google sign-in.
# Leave BLANK and no new accounts are ever created automatically —
# existing users can still link their Google identity and sign in.
GOOGLE_ALLOWED_DOMAIN=company.com
Where the redirect URI comes from: backend/src/lib/google-oauth.ts:35-37 builds it as FRONTEND_URL + /api/auth/google/callback. If your Cloudflare hostname differs from FRONTEND_URL for any reason, override it explicitly with GOOGLE_REDIRECT_URI — but note that docker-compose.yml does not currently pass that variable through to the backend, so you'd need to add it to the service's environment: block first.

11 Firewall

With no public IP there is no inbound path from the internet to close — the router already is the boundary. What is worth doing is limiting what the office LAN can reach.

From the internet
unreachable no public IP
From the LAN
:80 nginx
Via the tunnel
:443 Cloudflare edge
on the host (optional)bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow 22/tcp                       # SSH — don't lock yourself out
sudo ufw allow from 192.168.0.0/16 to any port 80 proto tcp   # LAN debug path
sudo ufw enable
sudo ufw status verbose
ufw does not filter published Docker ports. Docker writes its own iptables rules ahead of ufw's chain, so a container published with ports: stays reachable even with ufw denying that port. On this host that is acceptable — the LAN is trusted and the internet cannot reach it at all — but it is the reason a public-IP host must delete the ports: block rather than rely on the firewall.
confirm what is exposedbash
docker compose ps --format 'table {{.Service}}\t{{.Ports}}'
# Only nginx should show a port, and only 0.0.0.0:80->80/tcp.
# db, backend and frontend must be blank.

13 Cloudflare hardening

Optional, but this is most of the value of routing through Cloudflare at all.

Cloudflare Access — SSO in front of the whole app

Zero Trust → Access → Applications → Add an application → Self-hosted. Point it at and add a policy such as emails ending in @company.com. Visitors now authenticate at Cloudflare's edge before a single request reaches your VPS.

Access sits in front of the API too — including /api/auth/google/callback, which Google needs to reach without a session. If you enable Access and Google sign-in, add a Bypass policy for the path /api/auth/google/*, or the OAuth round-trip will dead-end at a Cloudflare login screen.

Cache rules

The SPA's hashed assets are safe to cache; the API never is. Zone → Caching → Cache Rules:

  • Bypass cache when URI path starts with /api/
  • Bypass cache when URI path starts with /uploads/ — or cache it; nginx already sets expires 7d, and floor plans rarely change

WAF and rate limiting

  • Security → WAF → enable the Cloudflare Managed Ruleset.
  • Add a rate-limiting rule on /api/auth/login — say 10 requests per minute per IP. The app has no login throttling of its own, so this is your only brute-force defence.
  • Optionally restrict by country if all your staff are in one place.
Worth knowing about the app's session model: tokens are stateless 24-hour JWTs with no server-side session table, and authMiddleware never re-checks users.status. Suspending a user does not invalidate their existing token, and neither does signing out. Cloudflare Access is currently the only practical way to cut off a departing employee immediately.

Back up the database and uploads

backup.shbash
#!/usr/bin/env bash
set -euo pipefail
cd ~/{{dir}}
STAMP=$(date +%F-%H%M)
mkdir -p ~/backups

# Postgres logical dump
docker compose exec -T db pg_dump -U opsmonitor opsmonitor \
  | gzip > ~/backups/opsmonitor-$STAMP.sql.gz

# Uploaded floor-plan images (named volume, not a bind mount)
docker run --rm \
  -v ops-monitor_uploads:/data:ro \
  -v ~/backups:/out alpine \
  tar czf /out/uploads-$STAMP.tar.gz -C /data .

# Keep 14 days
find ~/backups -name '*.gz' -mtime +14 -delete
schedule itbash
chmod +x ~/backup.sh
( crontab -l 2>/dev/null; echo "15 3 * * * ~/backup.sh" ) | crontab -
The volume name is prefixed by the project name. docker-compose.yml declares name: ops-monitor, so the volumes are ops-monitor_uploads and ops-monitor_pgdata. Confirm with docker volume ls before trusting the backup script.
