Deploy the Ops Monitoring Dashboard
on a single Ubuntu VPS

A self-contained, repeatable deployment: Nginx terminates HTTPS and serves the React SPA, proxies the API & uploads to the Bun/Hono backend, and Postgres runs alongside — all in Docker Compose, behind a Let's Encrypt certificate.

App-specific facts baked into this guide: the backend listens on PORT (default 3000), exposes /api/* and serves uploaded floor-plans from /uploads/* (written to backend/uploads). Floor-plan images can be up to 10 MB, so Nginx needs client_max_body_size ≥ that. The SPA calls the API same-origin (relative /api), so no CORS or build-time API URL is required.

Postgres and the backend are never published to the host — they're reachable only by service name (db, backend) inside opsnet. The attack surface is just Nginx on 80/443.

Request data flow

A signed-in admin loading the Workstation Map and dragging a pin:

Browser → Nginx (443). TLS handshake; request for /.
GET https://ops.example.com/
Nginx serves the SPA. try_files $uri /index.html returns the hashed JS/CSS bundle from disk — no backend hit.
root /usr/share/nginx/html
SPA authenticates. The React app posts credentials; Nginx proxies to the backend, which checks the bcrypt hash and returns a JWT (HS256, 24 h). The token is kept in localStorage.
POST /api/auth/login → backend:3000
Authorized reads. Every later call sends Authorization: Bearer …. The backend resolves the user's effective per-property role (Drizzle → Postgres) and returns floors + device pins.
GET /api/floors?hotelId=rh2 → db
Floor-plan images. Pin maps load background plans straight from the backend's static uploads dir (persisted on the uploads volume).
GET /uploads/flr-*.png → backend serveStatic
Drag a pin → persist. Repositioning issues an optimistic PATCH with the new % coordinates; a 403 comes back instead if the user lacks floors:crud.
PATCH /api/devices/:id { x, y } → db
Why same-origin matters: because Nginx serves the SPA and proxies /api under the same hostname, the browser never makes a cross-origin request — no CORS preflight, no third-party cookies, and the JWT is simply attached as a header by the app's fetch client.

1 Prerequisites

  • A VPS running Ubuntu 24.04 (DigitalOcean / Hetzner / Vultr / Linode …), 2 GB RAM+.
  • A domain with a DNS A record pointing to the VPS public IP — e.g. ops.example.com → 203.0.113.10. (TLS issuance needs this resolving first.)
  • SSH access as root or a sudo user, ideally with a key (not a password).
  • The app's seed credentials for first login: chai@richmond.local / admin123 (admin). Change these after first sign-in.

2 Harden the VPS & install Docker

Run as root on the fresh server. Creates a non-root deploy user, a firewall, and installs Docker Engine + the Compose plugin.

bootstrap.sh — run once on the VPS (root)bashCopy
# --- system updates ---
apt update && apt -y upgrade

# --- a non-root user that can run docker ---
adduser --disabled-password --gecos "" deploy
usermod -aG sudo deploy
# copy your SSH key to the new user so you can log in as 'deploy'
rsync --archive --chown=deploy:deploy ~/.ssh /home/deploy

# --- firewall: only SSH + web ---
apt -y install ufw
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable

# --- Docker Engine + Compose plugin (official convenience script) ---
curl -fsSL https://get.docker.com | sh
usermod -aG docker deploy

# --- (optional) basic brute-force protection ---
apt -y install fail2ban
systemctl enable --now fail2ban

echo "Done. Log back in as:  ssh deploy@YOUR_SERVER_IP"
From here on, work as the deploy user. Confirm Docker works without sudo: docker run --rm hello-world and docker compose version.

4 Dockerfiles

Backend — Bun + Hono API

A thin Bun image. bun install also pulls drizzle-kit so we can push the schema from inside the container later.

backend/DockerfiledockerfileCopy
FROM oven/bun:1-alpine
WORKDIR /app

# install deps first (better layer caching)
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile

# app source
COPY . .

# uploaded floor-plans are written here; mounted to a volume in compose
RUN mkdir -p uploads
ENV NODE_ENV=production
ENV PORT=3000
EXPOSE 3000

CMD ["bun", "src/index.ts"]

Frontend — build the SPA, serve via Nginx

Two stages: build the static bundle with Bun, then copy dist/ into an Nginx image. We run vite build directly (the tsc type-check is a CI gate, not needed to produce the bundle — and the app's @backend imports are type-only, so the backend isn't needed at build time).

frontend/DockerfiledockerfileCopy
# ---------- stage 1: build the SPA ----------
FROM oven/bun:1-alpine AS build
WORKDIR /app
COPY package.json bun.lock ./
RUN bun install --frozen-lockfile
COPY . .
# production bundle → /app/dist  (relative /api calls, so no API URL needed)
RUN bunx vite build

# ---------- stage 2: serve static files ----------
FROM nginx:1.27-alpine
# our server block lives in nginx/conf.d (bind-mounted by compose),
# so we only ship the built assets here
COPY --from=build /app/dist /usr/share/nginx/html
EXPOSE 80 443
Monorepo note: the build context is frontend/. If you prefer to also run the full bun run build (with tsc -b) inside Docker, set the context to the repo root and copy backend/ too, so the @backend/* path alias resolves. The vite build shown above avoids that entirely.

5 Nginx — proxy, SPA fallback, TLS

Edit the two server_name lines to your domain. Start with HTTPS commented out, enable it in step 9 once certs exist.

nginx/conf.d/default.confnginxCopy
# ---- HTTP :80 — ACME challenge + redirect to HTTPS ----
server {
    listen 80;
    server_name ops.example.com;

    # Let's Encrypt webroot challenge
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }
    # everything else → HTTPS (enable after step 9)
    location / {
        return 301 https://$host$request_uri;
    }
}

# ---- HTTPS :443 — the app ----
server {
    listen 443 ssl;
    http2 on;
    server_name ops.example.com;

    ssl_certificate     /etc/letsencrypt/live/ops.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/ops.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_prefer_server_ciphers off;

    # floor-plan uploads can be up to 10 MB
    client_max_body_size 12m;

    # compress text assets
    gzip on;
    gzip_comp_level 5;
    gzip_types text/css application/javascript application/json image/svg+xml;

    # security headers
    add_header X-Frame-Options SAMEORIGIN always;
    add_header X-Content-Type-Options nosniff always;
    add_header Referrer-Policy strict-origin-when-cross-origin always;

    # --- API → backend container ---
    location /api/ {
        proxy_pass http://backend:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }

    # --- uploaded floor-plan images → backend static ---
    location /uploads/ {
        proxy_pass http://backend:3000;
        proxy_set_header Host $host;
        expires 7d;
        add_header Cache-Control "public";
    }

    # --- the React SPA (client-side routing) ---
    root /usr/share/nginx/html;
    index index.html;

    # hashed assets — cache hard
    location /assets/ {
        expires 1y;
        add_header Cache-Control "public, immutable";
    }
    # app shell — never cache, always fall back to index.html
    location / {
        try_files $uri /index.html;
    }
}
Serving uploads directly (optional, faster): mount the uploads volume into nginx (read-only) and replace the /uploads/ block with root + try_files so Nginx serves the images without touching the backend. The proxy version above is simpler and works out of the box.

6 Compose file + secrets

Three services, three volumes, one network. restart: unless-stopped keeps everything up across reboots.

docker-compose.ymlyamlCopy
name: ops-monitor

services:
  db:
    image: postgres:17-alpine
    restart: unless-stopped
    environment:
      POSTGRES_DB: opsmonitor
      POSTGRES_USER: opsmonitor
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks: [opsnet]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U opsmonitor -d opsmonitor"]
      interval: 10s
      timeout: 5s
      retries: 5

  backend:
    build:
      context: ./backend
    restart: unless-stopped

Secrets — generate strong values

Compose auto-reads a file named .env next to the compose file. Generate the secrets, don't reuse the dev ones:

create the real .env (never commit)bashCopy
cat > .env <<EOF
DOMAIN=ops.example.com
DB_PASSWORD=$(openssl rand -base64 24 | tr -d /+=)
JWT_SECRET=$(openssl rand -base64 48 | tr -d /+=)
EOF
chmod 600 .env
cat .env   # note these down somewhere safe
.env.deploy.example — commit this templateCopy
DOMAIN=ops.example.com
DB_PASSWORD=change-me-strong
JWT_SECRET=change-me-very-long-random
Rotating the JWT secret logs everyone out (existing tokens become invalid). That's expected — set it once at first deploy and keep it stable.

8 Create the schema & seed data

Postgres already created the empty opsmonitor database (via POSTGRES_DB). Now push the Drizzle schema and load the demo data — run these once, inside the backend container.

one-time DB initbashCopy
# create all tables from the Drizzle schema
docker compose exec backend bun run db:push

# seed hotels, roles, users, floors, devices (demo accounts)
docker compose exec backend bun run db:seed
Seeding is for first launch / demos only. db:seed clears and repopulates the tables — never run it against a database that already holds real data. For real use, push the schema, then create your admin via the Access Control screen and skip the seed (or run it once, then change every demo password).
Schema changes later? This project uses drizzle-kit push (declarative). After pulling new code, re-run db:push. For audited migrations instead, switch to db:generate + db:migrate.

9 Enable HTTPS (Let's Encrypt)

Start Nginx on port 80 (so the ACME challenge is reachable), obtain a certificate, then it auto-loads on 443.

  1. Make sure your DNS A record already points at the VPS (verify: dig +short ops.example.com).
  2. Start Nginx (the HTTP block serves the challenge; the HTTPS block will fail to load until certs exist — temporarily comment the listen 443 server while issuing, or let it error and proceed):
issue the certificatebashCopy
docker compose up -d nginx

# run certbot once, sharing nginx's challenge + cert volumes
docker run --rm \
  -v ops-monitor_certbot-www:/var/www/certbot \
  -v ops-monitor_letsencrypt:/etc/letsencrypt \
  certbot/certbot certonly --webroot -w /var/www/certbot \
  -d ops.example.com \
  --email you@example.com --agree-tos --no-eff-email

# reload nginx to pick up the new certificate
docker compose exec nginx nginx -s reload

Add an auto-renewal: certbot certs last 90 days. A tiny cron entry on the host renews and reloads Nginx:

crontab -e (deploy user)cronCopy
# 03:30 daily — renew if due, then reload nginx
30 3 * * * docker run --rm -v ops-monitor_certbot-www:/var/www/certbot -v ops-monitor_letsencrypt:/etc/letsencrypt certbot/certbot renew --webroot -w /var/www/certbot --quiet && docker compose -f /home/deploy/ops/docker-compose.yml exec -T nginx nginx -s reload
Volume names are prefixed with the compose project name (name: ops-monitor) → ops-monitor_letsencrypt, etc. Check yours with docker volume ls.

#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."

echo "→ pulling latest code"
git pull --ff-only

echo "→ rebuilding images"
docker compose build

echo "→ restarting services"
docker compose up -d

echo "→ applying any schema changes"

Make it executable: chmod +x deploy/redeploy.sh — then redeploy with ./deploy/redeploy.sh. (Nginx rebuilds the SPA in its image, so the new frontend ships automatically.)

Backups — database + uploads

The only stateful data is Postgres and the uploaded floor-plans. Back up both:

deploy/backup.shbashCopy
#!/usr/bin/env bash
set -euo pipefail
cd "$(dirname "$0")/.."
STAMP=$(date +%Y%m%d-%H%M%S)
OUT=$HOME/backups
mkdir -p "$OUT"

echo "→ dumping database"
docker compose exec -T db pg_dump -U opsmonitor opsmonitor | gzip > "$OUT/db-$STAMP.sql.gz"

echo "→ archiving uploads volume"
docker run --rm -v ops-monitor_uploads:/data -v "$OUT":/backup alpine \
  tar czf "/backup/uploads-$STAMP.tar.gz" -C /data .

# keep the 14 most recent of each
ls -1t "$OUT"/db-*.sql.gz      | tail -n +15 | xargs -r rm
ls -1t "$OUT"/uploads-*.tar.gz | tail -n +15 | xargs -r rm
echo "✓ backup written to $OUT"
crontab — nightly backup at 02:00cronCopy
0 2 * * * /home/deploy/ops/deploy/backup.sh >> /home/deploy/backup.log 2>&1
Restore a DB dump: gunzip -c db-XXXX.sql.gz | docker compose exec -T db psql -U opsmonitor opsmonitor. Ship the backups off-box (rsync / S3) for real durability.

Security checklist

  • ✅ Firewall (ufw) allows only 22, 80, 443 — Postgres & the API are never published.
  • ✅ SSH key auth; disable password & root login in /etc/ssh/sshd_config (PasswordAuthentication no, PermitRootLogin no).
  • ✅ Strong, generated DB_PASSWORD and JWT_SECRET in .env (mode 600, never committed).
  • ✅ HTTPS enforced (HTTP → 301), modern TLS only, security headers set.
  • ✅ client_max_body_size caps uploads; the backend also validates type (PNG/JPG) & the 10 MB limit.
  • ✅ Change/delete all seeded demo accounts after first login.
  • 🔁 Keep the host patched (unattended-upgrades) and rebuild images periodically for base-image CVEs.
  • 🔁 Verify backups restore — a backup you've never restored isn't a backup.
Note on EXIF: uploaded images are stored as-is (the app doesn't strip metadata). If plans may carry sensitive EXIF, add a processing step (e.g. sharp) before going wide.

Troubleshooting

SymptomLikely cause & fix
502 Bad Gateway on /apiBackend down or DB not ready. docker compose logs backend; confirm db is healthy and DATABASE_URL host is db.
SPA loads but API 404 / wrong hostNginx location /api/ missing trailing slash or wrong upstream name. Must be proxy_pass http://backend:3000;.
Refreshing a route → 404SPA fallback missing. Ensure try_files $uri /index.html; in location /.
Cert issuance failsDNS A record not propagated, or port 80 blocked. dig +short DOMAIN; check ufw; ensure the HTTP server block serves /.well-known/acme-challenge/.
413 Request Entity Too LargeUpload > client_max_body_size. Raise it (≥ 12m) and nginx -s reload.
Everyone logged out after deployJWT_SECRET changed. Keep it stable across deploys.
Uploaded images 404 after restartThe uploads volume isn't mounted at /app/uploads, or you recreated the volume. Check the compose volumes:.
